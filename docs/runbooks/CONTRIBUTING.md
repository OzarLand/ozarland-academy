# Contributing

## Three ways to help, from the smallest

| You want to | Do this | What happens next |
|---|---|---|
| **Confirm a page**: it worked (or not) on your platform | Open a [Documentation proposal](https://github.com/OzarLand/ozarland-academy/issues/new?template=documentation-proposal.yml) and choose "I confirmed an existing page in my environment". Give the release, the deployment method and what you ran. Or use the "Tell us in one line" link at the end of the page. | A maintainer records it in the `confirmed_by` field of the page. A confirmation by a human operator on a real platform is what moves a page to `validated`. |
| **Fix an error** in a page | Use the file icon at the top right of the page to open its source on GitHub, edit it there and open a pull request. No local setup is needed. | The checks run on the pull request. If one fails on the front matter or on a link, say so in the pull request: the reviewer can fix it with you. |
| **Add a runbook** from a problem you solved | Follow the rules below. If you are not sure it fits, open a [Problem solved](https://github.com/OzarLand/ozarland-academy/issues/new?template=problem-solved.yml) issue first: a few lines are enough. | It is reviewed, merged as `draft`, then run on a lab. |

You deploy with something other than Kolla-Ansible (OpenStack-Ansible, Charmed OpenStack, a vendor distribution)?
Your variant is welcome: add a paragraph that starts with the name of your deployment method in bold, next to the
existing `**Kolla-Ansible:**` ones, and list the method in `deployment_methods`.

Today OzarLand has one maintainer, and pages are written, reviewed and run on labs with AI agents
([how OzarLand is built](https://github.com/OzarLand/ozarland/blob/main/docs/how-ozarland-is-built.md)). What only
you can bring is what happened on a real platform.

## Rules

This repository follows the OzarLand community contribution guide:
[CONTRIBUTING.md in `ozarland`](https://github.com/OzarLand/ozarland/blob/main/CONTRIBUTING.md).

In short:

1. Give context: OpenStack release, components, deployment method, environment conditions, what you checked.
2. No sensitive data: no secrets, real hostnames, domains, IP or MAC addresses, customer or person names,
   unredacted logs ([how to redact](https://github.com/OzarLand/ozarland/blob/main/docs/conventions/sensitive-data.md)).
3. Flag risky commands: ⚠️ state-changing, 🛑 destructive
   ([risk warnings](https://github.com/OzarLand/ozarland/blob/main/docs/conventions/risk-warnings.md)).
4. Say where it was observed; never present a procedure as universal.
5. Copy the template [`templates/runbook.md`](https://github.com/OzarLand/ozarland-academy/blob/main/docs/runbooks/templates/runbook.md) (it is read on GitHub, not on the site), open a pull request, sign off your commits (`git commit -s`).

Repository-specific notes:

- Put the page in the directory of its primary symptom (`lifecycle/`, `scheduling/`, `migration/`, `networking/`,
  `volumes/`, `recovery/`); cross-cutting investigation guides go in `diagnostics/`, guides to reading a
  service's logs in `logs/`.
- Name the file after the symptom, lowercase, hyphenated: `instance-stuck-in-build-waiting-for-vif-plugged.md`.
- Add the page to the index table of [index.md](index.md) and to the `nav` of `docs/runbooks.toml` in the same pull request. Then run `python3 tools/site/runbook_categories.py`, which rewrites the index page of the category.
  The status counts shown on the hub are regenerated by the maintainers: you do not need to run anything for them.
