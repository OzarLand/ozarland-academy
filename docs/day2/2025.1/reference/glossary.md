# Glossary

The terms the study uses, with the place where each is defined. Each meaning holds for Kolla-Ansible `2025.1-eom`
and ansible-core 2.18.20; a term that only applied to an earlier release says so.

| Term | Meaning in this study | Defined in |
|---|---|---|
| loop-notify | When any item of a looped task changes, ansible-core 2.18.20 marks the whole task changed (`lib/ansible/executor/task_executor.py:138-140`) and notifies the handlers named by the task (`lib/ansible/executor/task_executor.py:850-851`, `lib/ansible/plugins/strategy/__init__.py:648-661`). **Changed in 2025.1:** Kolla no longer relies on it to restart containers. The config step of almost every role notifies no handler, and the shared `check-containers` step builds its `notify` list from the items that changed only, in a separate task (`roles/service-check-containers/tasks/main.yml:34-41`), so a change that concerns one container no longer notifies the handlers of every container of the role on that host [CODE]. Whether that holds on a real run is [NOT AVAILABLE]. | [Tags §2.4](../risk/tags.md#24-loop-notify-is-gone-in-20251-code); as a finding: [Findings](findings.md#headline-findings) ([F1](findings.md#f1)) |
| `common_run` | **Ussuri only.** The per-host fact that guarded the `common` role, run through role dependencies in the first play in which a host appeared. In 2025.1 no file in `ansible/` or `kolla_ansible/` mentions it: `common` is a play of its own with the `common` tag (`site.yml:88-103`), run once per run that executes that play [CODE]. | [Repository architecture §5.1](../concepts/repository-architecture.md#51-the-common-role-and-the-common_run-guard) |
| `COPY_ALWAYS` / `COPY_ONCE` (`config_strategy`) | `COPY_ALWAYS`, the default (`group_vars/all.yml:49`): `kolla_set_configs` copies the config and applies permissions on every container start. `COPY_ONCE`: only on the first start of a container (kolla `docker/base/set_configs.py:562-577`), and the restart handler then always recreates the container, so only a recreate re-applies config (`module_utils/kolla_docker_worker.py:364`, `module_utils/kolla_podman_worker.py:618`) [CODE]. | [Kolla images §2.3](../concepts/kolla-images.md#23-kolla_set_configs-copy-and-permissions), [Kolla images §3.5](../concepts/kolla-images.md#35-what-a-restart-applies); [Repository architecture §7](../concepts/repository-architecture.md#7-configuration-generation-and-overrides) (item 4) |
| `kolla_container` (`kolla_container_engine`) | The module that drives every container of the service roles. **Changed in 2025.1:** it has 13 actions (`library/kolla_container.py:273-285`); `get_container_env` and `get_container_state` moved to `kolla_container_facts` (`library/kolla_container_facts.py:226-231`), and `kolla_container_volume_facts` is gone. It uses a Docker worker when `container_engine` is `docker` and a Podman worker otherwise (`library/kolla_container.py:411-416`); the roles pass `kolla_container_engine`, default `docker` (`group_vars/all.yml:100,162`) [CODE]. | [Repository architecture §6](../concepts/repository-architecture.md#6-custom-modules--container-lifecycle-via-kolla_container) |
| one-shot container | A container that Kolla-Ansible starts with `kolla_container` `start_container`, `detach: False`, `restart_policy: oneshot` and a variable that selects a branch of the image's start script (e.g. `roles/keystone/tasks/bootstrap_service.yml:34-52`); the branch ends in `exit 0` before the service command (kolla `docker/keystone/keystone/extend_start.sh:43-46`). It is started directly, not through systemd: with Docker it gets no unit file (`module_utils/kolla_docker_worker.py:349-350,392-393`); with Podman a unit file is written at creation but not used to start it (`module_utils/kolla_podman_worker.py:606,643-645`) [CODE]. In the command sections of the [Operations](../operations/index.md) pages, "One-shot" means bootstrap containers that run regardless of drift. | [Kolla images §4](../concepts/kolla-images.md#4-one-shot-containers-what-the-environment-variables-run); the convention of the command sections is in [Operations](../operations/index.md#conventions-used-by-the-command-sections) |
| drift | What `compare_container` detects: a missing container, a changed image or container parameter, a systemd unit file that would change, or `kolla_set_configs --check` reporting a difference (`module_utils/kolla_container_worker.py:58-65`). With Docker the check counts as a difference on exit 1, on an exec killed with 137, or on a failed `docker exec` (`module_utils/kolla_docker_worker.py:146-181`); with Podman on exit 1, a failed exec, or a container that is not running, and any other exit code is an error (`module_utils/kolla_podman_worker.py:524-552`) [CODE]. **Changed in 2025.1:** `kolla_set_configs --check` also exits 1 when the container's running command differs from `config.json`, or when a file of the saved defaults state is no longer in `config.json` (kolla `docker/base/set_configs.py:580-643`), so there are more ways to drift. The unit file template also changed (`PartOf=kolla.target`, `module_utils/kolla_systemd_worker.py:27`), so a unit written by 2024.1 counts as drift at the first 2025.1 check [CODE]. | [Operations, "Drift"](../operations/index.md#drift); mechanism: [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern) |
| restart vs recreate | The restart handler calls `recreate_or_restart_container`: **recreate** (stop → rm → create → start) when the image or parameters differ or under `COPY_ONCE`, otherwise **restart**, a systemd `RestartUnit` of the container's `kolla-<name>-container.service` (Docker `module_utils/kolla_docker_worker.py:352-374,450-467`; Podman `module_utils/kolla_podman_worker.py:609-626,704-713`; `module_utils/kolla_systemd_worker.py:72,107-114`). Both are full stop/start cycles; the unit's stop waits up to `docker_graceful_timeout` (60 s) (`module_utils/kolla_systemd_worker.py:33`, `group_vars/all.yml:148,160`) [CODE]. The same holds with Docker and with Podman. | [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern) |
| `flush_handlers` | `meta: flush_handlers` is where the notified restart handlers run: at the end of most `deploy.yml` (e.g. `roles/nova/tasks/deploy.yml:8-9`), or else at the end of the play. The loadbalancer role (haproxy, keepalived, proxysql) deliberately defers to the end of its play (`roles/loadbalancer/tasks/deploy.yml:8-11`) [CODE]. | [Execution flow §1](../concepts/deployment-execution-flow.md#1-how-the-order-is-decided) (row "Handler flush points"), [Execution flow §3](../concepts/deployment-execution-flow.md#3-inside-a-role-the-standard-deploy-sequence) (step 6) |
| serial / batch (`kolla_serial`) | `serial` splits a play into batches; each batch completes the whole play, handlers included, before the next starts (ansible-core 2.18.20 `lib/ansible/executor/playbook_executor.py:179-188`). **Changed in 2025.1:** `ANSIBLE_SERIAL` is gone. `upgrade` and `reconfigure` always add `-e kolla_serial=0` (`kolla_ansible/cli/commands.py:20-22,136,278`), after the user's own `-e` options (`kolla_ansible/ansible.py:261-266`); ansible-core merges the `-e` options in order, a later value replacing an earlier one (ansible-core 2.18.20 `lib/ansible/utils/vars.py:94-105, :198-224`), so a user `-e kolla_serial=N` cannot batch these two commands [CODE]; no run has confirmed it. For `deploy` and the other commands, which set no `kolla_serial`, pass `-e kolla_serial=N` yourself (`kolla_ansible/cli/commands.py:231-242`). The etcd play has no `serial` key, so `kolla_serial` does not batch it (`site.yml:485-496`) [CODE]. | [Execution flow §5](../concepts/deployment-execution-flow.md#5-batching-serial-and-its-interaction-with-order), [Execution flow §1](../concepts/deployment-execution-flow.md#1-how-the-order-is-decided); [Repository architecture §2](../concepts/repository-architecture.md#2-from-cli-to-ansible-playbook) |
| `max_fail_percentage` | Set on almost every play from `<service>_max_fail_percentage`, then `kolla_max_fail_percentage`, then 100 (e.g. `site.yml:96-99`). ansible-core 2.18.20 compares the hosts failed in the current batch with the batch size (`lib/ansible/plugins/strategy/linear.py:335-347`, `lib/ansible/executor/task_queue_manager.py:328-334`), so with the default 100 it never stops a play early [CODE]. | [Execution flow §5](../concepts/deployment-execution-flow.md#5-batching-serial-and-its-interaction-with-order) |
| `run_once` / `delegate_to` | `run_once`: the task runs once per play, or once per batch when `kolla_serial` > 0, since each batch is a separate run of the play and `run_once` only ends the host loop of that run (ansible-core 2.18.20 `lib/ansible/executor/playbook_executor.py:179-188`, `lib/ansible/plugins/strategy/linear.py:178,204-206`) [CODE]. `delegate_to`: the step runs on another host; `groups['<grp>'][0]` is the target of almost every `run_once`/`delegate_to` bootstrap step, including for hosts outside `--limit`. | [Tags §2.5](../risk/tags.md#25-run_once-with-serial-code); [Repository architecture §8](../concepts/repository-architecture.md#8-inventory-model); [Reconfigure a single service §2](../operations/reconfigure-a-service.md#2-execute-a-service-specific-tag-implicit-effects) (row "Actions on hosts outside `--limit`") |
| `genconfig` | The CLI command for `kolla_action=config` (`kolla_ansible/cli/commands.py:113-125`): it writes the config and compares no container. **Changed in 2025.1:** it no longer pulls the fluentd image, and two config tasks can still restart a container: `placement-api` with the Apache WSGI provider and `cinder-volume` with Huawei XML files ([Conventions](../start/conventions.md#operation-impact-classes), row `writes-config`) [CODE]. | [Execution flow §4](../concepts/deployment-execution-flow.md#4-action-matrix-what-each-kolla_action-does) (row `genconfig`); [Repository architecture §2](../concepts/repository-architecture.md#2-from-cli-to-ansible-playbook) |
| `deploy-containers` | Runs the role's `deploy-containers.yml` (`kolla_action=deploy-containers`, `kolla_ansible/cli/commands.py:245-256`), which in 51 of the 53 roles that have one is only an import of `check-containers.yml` (e.g. `roles/nova-cell/tasks/deploy-containers.yml:2`), plus the handlers it notifies: no config is written, and no bootstrap, Keystone registration or loadbalancer configuration runs (the loadbalancer includes require `deploy`, `reconfigure`, `upgrade` or `config`, `site.yml:327`). The exceptions are mariadb, which also looks up the cluster (`roles/mariadb/tasks/deploy-containers.yml`), and ceph-rgw, whose file is empty [CODE]. Swift, an exception in 2024.1, has no role in 2025.1. | [Execution flow §4](../concepts/deployment-execution-flow.md#4-action-matrix-what-each-kolla_action-does) (row `deploy-containers`); [Write config first, apply in controlled batches §1.1](../operations/controlled-batches.md#11-compute-changes-in-controlled-batches-recommended-pattern) |
| `KOLLA_BOOTSTRAP` / `KOLLA_UPGRADE` / `KOLLA_OSM` | Variables, sent with an empty value (`module_utils/kolla_container_worker.py:547-554`), that select a one-shot branch of an image's start script; the branch tests only whether the variable is set (e.g. kolla `docker/keystone/keystone/extend_start.sh:43`). What each one runs differs per image [CODE]. | [Kolla images §4](../concepts/kolla-images.md#4-one-shot-containers-what-the-environment-variables-run) |
| [CODE] / [NOT AVAILABLE] | The two evidence labels: shown by the sources, with a `path:line` citation nearby; or not established by the sources. The fact sheets use FACT and NOT AVAILABLE for the same two levels. | [Conventions and evidence labels](../start/conventions.md#evidence-labels) |
| `kolla_action` | The extra var that each CLI command passes (`extra_vars["kolla_action"]`, e.g. `kolla_ansible/cli/commands.py:238`); every service role's `tasks/main.yml` is a dynamic `include_tasks: "{{ kolla_action }}.yml"` (e.g. `roles/nova-cell/tasks/main.yml:2`) [CODE]. New value in 2025.1: `check` (`kolla_ansible/cli/commands.py:502`). | [Repository architecture §2](../concepts/repository-architecture.md#2-from-cli-to-ansible-playbook), [Repository architecture §4.1](../concepts/repository-architecture.md#41-kolla_action-dispatch) |
| `compare_container` | The `kolla_container` action run by `check-containers.yml`, which in 2025.1 imports the shared `service-check-containers` role (e.g. `roles/nova-cell/tasks/check-containers.yml:2-3`; `roles/service-check-containers/tasks/main.yml:4-29`): it compares the container's definition and its systemd unit file, and runs `kolla_set_configs --check` inside the running container (`module_utils/kolla_container_worker.py:58-65`) [CODE]. | [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern) |
| `kolla_set_configs --check` | The in-container check whose exit code decides config drift. **Changed in 2025.1:** it checks the running command against `config.json`, then that every file of the saved defaults state is still in `config.json`, then the `config_files` entries (kolla `docker/base/set_configs.py:580-643,655-657`); any difference exits 1 (`:41-44,660-662`) [CODE]. The 2024.1 statement that it compares only the `config_files` entries ([F14](findings.md#f14)) no longer holds. | [Kolla images §3](../concepts/kolla-images.md#3-kolla_set_configs---check-what-it-compares-and-its-exit-codes); by hand: [Predict and inspect a run](../operations/predict-a-run.md) |
| `config.json` (`config_files`, `command`, `permissions`) | The manifest, read from `/var/lib/kolla/config_files/config.json`, that tells `kolla_set_configs` which files to copy to their final location, and names the command to start, written to `/run_command` (kolla `docker/base/set_configs.py:292-332`) [CODE]. | [Repository architecture §7](../concepts/repository-architecture.md#7-configuration-generation-and-overrides) (item 4); [Kolla images §2.3](../concepts/kolla-images.md#23-kolla_set_configs-copy-and-permissions) |
| global inputs | `enable_*` flags, group membership and passwords, which are rendered into per-host files on every host. Examples: the RPC transport URL lists every host of the RPC group with its password (`group_vars/all.yml:269,274`), and the cron logrotate list follows the global `enable_*` flags (`roles/common/tasks/config.yml:171-185`) [CODE]. | [Component dependencies §5](../components/dependencies.md#5-compute-node-dependency-summary); [Why a small change creates a large workload](../risk/small-change-large-workload.md) |
| waves, forks | A task on *H* hosts needs ⌈H/F⌉ waves, where *F* is the number of forks. This is a counting model: ansible-core 2.18.20 starts at most min(forks, batch size) workers and queues a host's task only on a free worker (`lib/ansible/executor/task_queue_manager.py:316-317`, `lib/ansible/plugins/strategy/__init__.py:396-424`) [CODE]. **Changed in 2025.1:** the CLI has no `--forks` option any more (`kolla_ansible/ansible.py:30-125`); forks come from the Ansible configuration only. | [Compute scaling §1](../concepts/compute-scaling-and-performance.md#1-how-ansible-core-218-spends-time-in-kolla-ansible), [Compute scaling §4.1](../concepts/compute-scaling-and-performance.md#41-model) |
| scope legend D, Ctl, C, C×S, H, Cond | How often a task runs: once per deployment, per controller, per compute, per compute and container, per host, or only when a condition holds. | [Compute scaling §3](../concepts/compute-scaling-and-performance.md#3-expensive-tasks-and-their-scaling-factors) |
| R*n*, F*n*, Q*n* | Risk numbers in the [Risk register](../risk/risk-register.md#r1), finding numbers in [Findings](findings.md#f1) and open-question numbers in [Open questions](../troubleshooting/open-questions.md#q1). Each risk, finding and question is a section with its own anchor, so links to them land on the item. | [Risk register](../risk/risk-register.md#matrix); [Findings](findings.md#headline-findings); [Open questions](../troubleshooting/open-questions.md) |
