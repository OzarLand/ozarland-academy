# Troubleshooting

Where to look when a `kolla-ansible` run did something unexpected, or did nothing. Each row of the [symptom
index](#symptom-index) names what an operator sees, restates what the study says the code does, and links to the section
that establishes it. The page also says where to look for one component, what is already known as a bug or as an open
point, and which checks the study names.

> [!IMPORTANT]
> The study rests only on reading source code: kolla-ansible `ussuri-eol`, the kolla image repository `ussuri-eol` and
> the Ansible 2.9.27 source. Nothing was run against a host, there are no timings, and every statement about data-plane
> or VM impact is [NOT AVAILABLE] ([Limits of this study](../reference/method-and-limits.md#limits-of-this-study)). All
> conclusions come from the Ussuri implementation, not from newer releases.
>
> During an incident, the portal can tell what Kolla will do given the inputs: tasks and restarts. What that does to VMs
> and APIs depends on the environment and is mostly [NOT AVAILABLE] in these sources ([Code guarantees and environment
> dependence](../operations/index.md#code-guarantees-and-environment-dependence)).
>
> This page is an index. It adds no diagnosis and no procedure of its own.

## Symptom index

Three mechanisms explain almost every surprise on the operation pages: config drift means a full container stop/start,
never a reload; loop-notify, where one changed container in a role's loop restarts every container of that role on that
host; and global inputs, which are rendered into per-host files on every host ([Three mechanisms that explain almost
every surprise](../operations/index.md#three-mechanisms-that-explain-almost-every-surprise)).

In the tables, "What the code does" restates what the sections linked under "Read" say, and keeps their evidence labels.
Rows that restate a fact sheet carry the words of the fact sheets, FACT and NOT AVAILABLE, which name the same two
levels as [CODE] and [NOT AVAILABLE] ([Evidence labels](../start/conventions.md#evidence-labels)). A sentence without a
label restates a sentence that carries none.

### Cases the study does not solve

The study does not diagnose a runtime failure of OpenStack, such as a failed VM deployment: no container or VM behaviour
is used as evidence ([Limits of this study](../reference/method-and-limits.md#limits-of-this-study)). For these classic
cases it offers the dependencies and the restarts read from the code, and marks the rest as open.

| Case | What the study offers | What it does not establish |
|---|---|---|
| An instance fails to boot or to be scheduled (a VM deployment fails) | [Nova deep dive §3](../components/nova-deep-dive.md#3-what-must-be-available-before-nova-can-operate) lists what must be available before Nova can operate, ordered by necessity: MariaDB, RabbitMQ, Keystone and memcached, Placement, cell mapping and host mapping, Neutron server and an L2 agent on the compute, Glance and Cinder, libvirt. [Nova deep dive §2.2](../components/nova-deep-dive.md#22-runtime-dependencies-what-nova-needs-to-operate) gives what each Nova component requires at runtime. [Component dependencies §1](../components/dependencies.md#1-the-shared-substrate-what-every-openstack-service-uses) and [Component dependencies §3](../components/dependencies.md#3-control-plane-services) give the shared substrate and the control-plane services. | Upstream Nova behaviour is not in these sources and is marked [NOT AVAILABLE]. Diagnosing the runtime failure itself is outside what the sources establish. |
| A new compute gets no instances | [Nova deep dive §3](../components/nova-deep-dive.md#3-what-must-be-available-before-nova-can-operate) (item 5): the scheduler does not discover hosts by itself (`discover_hosts_in_cells_interval = -1`). [Add a compute node §2](../operations/add-a-compute-node.md#2-add-a-compute-node) says what `deploy --limit` runs for a new compute. [Reconfigure Neutron §4](../operations/reconfigure-neutron.md#4-impact-on-networking) gives, per component, what a restart does in the code. | For neutron-server and the OVS, L3, DHCP and metadata agents, the effect of a restart on existing connectivity is marked [NOT AVAILABLE] ([What is not known, "Network data plane"](what-is-not-known.md#network-data-plane)). |

| A volume cannot be attached | [Component dependencies §2](../components/dependencies.md#2-infrastructure-components) (row "iscsid / tgtd"): nova-compute (volume attach) and cinder-volume (LVM) depend on it. NOT AVAILABLE: whether existing attachments survive a cinder-volume restart. |
