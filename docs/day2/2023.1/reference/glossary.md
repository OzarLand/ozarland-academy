# Glossary

The terms the study uses, with the place where each is defined. Each meaning holds for Kolla-Ansible `2023.1-eol`
and ansible-core 2.14.18; a term that only applied to Ussuri says so.

| Term | Meaning in this study | Defined in |
|---|---|---|
| loop-notify | When any item of a looped task changes, ansible-core 2.14 notifies the handlers of every executed (non-skipped) item. Kolla's `config.yml` and `check-containers.yml` loop over `<role>_services`, so a change that concerns one container restarts every container of that role on that host [CODE]. | [Tags §2.4](../risk/tags.md#24-loop-notify-one-changed-item-notifies-the-handlers-of-all-items-code); as a finding: [Findings](findings.md#headline-findings) ([F1](findings.md#f1)) |
| `common_run` | **Ussuri only.** The per-host fact that guarded the `common` role, run through role dependencies in the first play in which a host appeared. In 2023.1 no file in `ansible/` or `tools/` mentions it: `common` is a play of its own with the `common` tag (`site.yml:86-97`), run once per run that executes that play [CODE]. | [Repository architecture §5.1](../concepts/repository-architecture.md#51-the-common-role-and-the-common_run-guard) |
| `COPY_ALWAYS` / `COPY_ONCE` (`config_strategy`) | `COPY_ALWAYS`, the default (`group_vars/all.yml:43`): `kolla_set_configs` copies the config and applies permissions on every container start. `COPY_ONCE`: only on the first start of a container, so only a recreate re-applies config [CODE]. | [Kolla images §2.3](../concepts/kolla-images.md#23-kolla_set_configs-copy-and-permissions), [Kolla images §3.5](../concepts/kolla-images.md#35-what-a-restart-applies); [Repository architecture §7](../concepts/repository-architecture.md#7-configuration-generation-and-overrides) (item 4) |
| one-shot container | A container that Kolla-Ansible starts with `kolla_docker` `start_container`, `detach: False`, `restart_policy: oneshot` (no systemd unit is created for it) and a variable that selects a branch of the image's start script; the branch ends in `exit 0` before the service command [CODE]. In the command sections of the [Operations](../operations/index.md) pages, "One-shot" means bootstrap containers that run regardless of drift. | [Kolla images §4](../concepts/kolla-images.md#4-one-shot-containers-what-the-environment-variables-run); the convention of the command sections is in [Operations](../operations/index.md#conventions-used-by-the-command-sections) |
| drift | What `compare_container` detects: a missing container, a changed image or container parameter, a systemd unit file that would change, or `kolla_set_configs --check` reporting a difference (exit 1, an exec killed with 137, or a failed `docker exec`) [CODE]. | [Operations, "Drift"](../operations/index.md#drift); mechanism: [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern) |
| restart vs recreate | The restart handler calls `recreate_or_restart_container`: **recreate** (stop → rm → create → start) when the image or parameters differ or under `COPY_ONCE`, otherwise **restart** (in 2023.1 a systemd `RestartUnit` of the container's `kolla-<name>-container.service`). Both are full stop/start cycles; the stop waits up to `docker_graceful_timeout` (60 s) [CODE]. | [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern) |
| `flush_handlers` | `meta: flush_handlers` is where the notified restart handlers run: at the end of most `deploy.yml`, or else at the end of the play. The loadbalancer role (haproxy, keepalived, proxysql) deliberately defers to the end of its play. | [Execution flow §1](../concepts/deployment-execution-flow.md#1-how-the-order-is-decided) (row "Handler flush points"), [Execution flow §3](../concepts/deployment-execution-flow.md#3-inside-a-role-the-standard-deploy-sequence) (step 6) |
| serial / batch (`kolla_serial`, `ANSIBLE_SERIAL`) | `serial` splits a play into batches; each batch completes the whole play, handlers included, before the next starts. For `reconfigure` and `upgrade` the wrapper sets `kolla_serial` from `ANSIBLE_SERIAL`; for `deploy`, pass `-e kolla_serial=N` yourself. | [Execution flow §5](../concepts/deployment-execution-flow.md#5-batching-serial-and-its-interaction-with-order), [Execution flow §1](../concepts/deployment-execution-flow.md#1-how-the-order-is-decided); [Repository architecture §2](../concepts/repository-architecture.md#2-from-cli-to-ansible-playbook) |
| `run_once` / `delegate_to` | `run_once`: the task runs once per play, or once per batch when `kolla_serial` > 0 [CODE]. `delegate_to`: the step runs on another host; `groups['<grp>'][0]` is the target of almost every `run_once`/`delegate_to` bootstrap step, including for hosts outside `--limit`. | [Tags §2.5](../risk/tags.md#25-run_once-with-serial-code); [Repository architecture §8](../concepts/repository-architecture.md#8-inventory-model); [Reconfigure a single service §2](../operations/reconfigure-a-service.md#2-execute-a-service-specific-tag-implicit-effects) (row "Actions on hosts outside `--limit`") |
| `genconfig` | The CLI command for `kolla_action=config`: it writes the config, compares no container, and all container restarts are skipped (the Ussuri exception, the nova-hyperv handlers, is gone: 2023.1 has no nova-hyperv role; [Pre-execution checklist](../operations/pre-execution-checklist.md)). | [Execution flow §4](../concepts/deployment-execution-flow.md#4-action-matrix-what-each-kolla_action-does) (row `genconfig`); [Repository architecture §2](../concepts/repository-architecture.md#2-from-cli-to-ansible-playbook) |
| `deploy-containers` | Runs only `check-containers.yml` and the handlers it notifies: no config is written, and no bootstrap, Keystone registration or loadbalancer configuration runs. | [Execution flow §4](../concepts/deployment-execution-flow.md#4-action-matrix-what-each-kolla_action-does) (row `deploy-containers`); [Write config first, apply in controlled batches §1.1](../operations/controlled-batches.md#11-compute-changes-in-controlled-batches-recommended-pattern) |
| `KOLLA_BOOTSTRAP` / `KOLLA_UPGRADE` / `KOLLA_OSM` | Variables, sent with an empty value, that select a one-shot branch of an image's start script. What each one runs differs per image [CODE]. | [Kolla images §4](../concepts/kolla-images.md#4-one-shot-containers-what-the-environment-variables-run) |
| [CODE] / [NOT AVAILABLE] | The two evidence labels: shown by the sources, with a `path:line` citation nearby; or not established by the sources. The fact sheets use FACT and NOT AVAILABLE for the same two levels. | [Conventions and evidence labels](../start/conventions.md#evidence-labels) |
| `kolla_action` | The extra-var that the wrapper passes with a sub-command (`-e kolla_action=<action>`); every service role's `tasks/main.yml` is a dynamic `include_tasks: "{{ kolla_action }}.yml"`. | [Repository architecture §2](../concepts/repository-architecture.md#2-from-cli-to-ansible-playbook), [Repository architecture §4.1](../concepts/repository-architecture.md#41-kolla_action-dispatch) |
| `compare_container` | The `kolla_docker` action run by `check-containers.yml`: it compares the container's definition and runs `kolla_set_configs --check` inside the running container. | [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern) |
| `kolla_set_configs --check` | The in-container check whose exit code decides config drift. It compares only the `config_files` entries of `config.json` [CODE] ([F14](findings.md#f14)). | [Kolla images §3](../concepts/kolla-images.md#3-kolla_set_configs---check-what-it-compares-and-its-exit-codes); by hand: [Predict and inspect a run](../operations/predict-a-run.md) |
| `config.json` (`config_files`, `command`, `permissions`) | The manifest that tells `kolla_set_configs` which files to copy from `/var/lib/kolla/config_files` to their final location, and names the command to start. | [Repository architecture §7](../concepts/repository-architecture.md#7-configuration-generation-and-overrides) (item 4); [Kolla images §2.3](../concepts/kolla-images.md#23-kolla_set_configs-copy-and-permissions) |
| global inputs | `enable_*` flags, group membership and passwords, which are rendered into per-host files on every host. | [Component dependencies §5](../components/dependencies.md#5-compute-node-dependency-summary); [Why a small change creates a large workload](../risk/small-change-large-workload.md) |
| waves, forks | A task on *H* hosts needs ⌈H/F⌉ waves, where *F* is the number of forks. | [Compute scaling §1](../concepts/compute-scaling-and-performance.md#1-how-ansible-core-214-spends-time-in-kolla-ansible), [Compute scaling §4.1](../concepts/compute-scaling-and-performance.md#41-model) |
| scope legend D, Ctl, C, C×S, H, Cond | How often a task runs: once per deployment, per controller, per compute, per compute and container, per host, or only when a condition holds. | [Compute scaling §3](../concepts/compute-scaling-and-performance.md#3-expensive-tasks-and-their-scaling-factors) |
| R*n*, F*n*, Q*n* | Risk numbers [R1–R25](../risk/risk-register.md#r1), finding numbers [F1–F15](findings.md#f1) and open-question numbers [Q1–Q14](../troubleshooting/open-questions.md#q1). Each risk, finding and question is a section with its own anchor, so links to them land on the item. | [Risk register](../risk/risk-register.md#matrix); [Findings](findings.md#headline-findings); [Open questions](../troubleshooting/open-questions.md) |
