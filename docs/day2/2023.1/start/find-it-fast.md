## Where the final-objective questions are answered

| Question | Short answer | Details |
|---|---|---|
| If I execute a specific tag, exactly what happens? | The tagged plays run on all their hosts. The haproxy frontend of that service, if it has one, is re-rendered. `common` does not run: in 2023.1 it is its own play, tagged `common` only. For API services, Keystone registration and DB-sync containers run (Neutron's included, on `deploy` and `reconfigure`). Handlers restart drifted containers, plus their role siblings | [Tags §3](../risk/tags.md#3-what-a-tag-really-executes-master-table), [Reconfigure a single service §2](../operations/reconfigure-a-service.md#2-execute-a-service-specific-tag-implicit-effects), [Components](../components/index.md) |
| Which OpenStack components are affected? | The tagged service, plus HAProxy (only if its frontend changed). fluentd/cron/kolla_toolbox only under `-t common` or a run without tags (if `common` drifted) | [Reconfigure a single service §2](../operations/reconfigure-a-service.md#2-execute-a-service-specific-tag-implicit-effects) |
| Which compute nodes will receive changes? | Every compute in the play's host patterns (`common`, `nova`, `nova-cell`, `neutron`, `openvswitch`, `iscsi`, …) runs the tasks. Restarts happen where drift exists, usually all or none, because inputs are global | [Compute scaling §2](../concepts/compute-scaling-and-performance.md#2-work-per-compute-host-read-from-the-task-files), [Reconfigure Nova §4](../operations/reconfigure-nova.md#4-are-all-compute-nodes-affected-does-nova-compute-restart-on-every-compute) |
| Will containers restart or be recreated? | Restart (systemd unit restart, stop timeout `docker_graceful_timeout`, 60 s) on config drift. Recreate on image or parameter change. Siblings in the same role restart too. On a run with nothing to apply, a restart needs a notifying task that reports changed, and `check-containers` reports changed only for a missing or not-running container, a differing compared parameter, a missing or differing systemd unit file, or a `kolla_set_configs --check` exit 1/137 or Docker client error [CODE]. Whether no notifying task reports changed on an unchanged cloud is [NOT AVAILABLE], with one known exception [CODE]: containers whose `config.json` has an entry that `kolla_set_configs --check` always reports as drift (e.g. `prometheus_server` once files exist under `/etc/kolla/config/prometheus/extras/`: that `preserve_properties` entry has no `perm`) restart on every deploy/reconfigure | [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern), [Tags §3](../risk/tags.md#3-what-a-tag-really-executes-master-table), [Tags §2.4](../risk/tags.md#24-loop-notify-one-changed-item-notifies-the-handlers-of-all-items-code), [Kolla images §3](../concepts/kolla-images.md#3-kolla_set_configs---check-what-it-compares-and-its-exit-codes) |
| Can running VMs be impacted? | The restarts that the study traces to running VMs include `nova_libvirt` (frequent, via loop-notify), OVS/vswitchd and the L3 agent [CODE]. Whether VMs survive a libvirt restart, and whether their traffic is interrupted, is [NOT AVAILABLE] | [Nova deep dive §5](../components/nova-deep-dive.md#5-nova-libvirt-why-its-restart-is-special), [Risk register](../risk/risk-register.md) [R1](../risk/risk-register.md#r1)/[R6](../risk/risk-register.md#r6)/[R7](../risk/risk-register.md#r7), [Findings](../reference/findings.md) [Q1–Q4](../troubleshooting/open-questions.md#q1) |
| What is the execution order? | `site.yml` play order (no dependency resolver); within a role: register → config → check → bootstrap → flush | [Execution flow](../concepts/deployment-execution-flow.md) |
| Which tasks can take hours with hundreds of computes? | Per-compute task chains multiplied by ⌈C/forks⌉ waves, serial fact gathering under `--limit`, image pulls (one per container placed on the compute, [Component dependencies §5](../components/dependencies.md#5-compute-node-dependency-summary)), per-batch waits under `serial` | [Compute scaling §3–4](../concepts/compute-scaling-and-performance.md#3-expensive-tasks-and-their-scaling-factors) |
| Why does a small change generate a large workload? | Global inputs are rendered into per-host files; loop-notify; every run re-executes the full per-host chain | [Compute scaling §5](../concepts/compute-scaling-and-performance.md#5-why-a-small-change-becomes-a-large-workload), [Why a small change creates a large workload](../risk/small-change-large-workload.md) |
| How can I minimise the operational impact? | `genconfig` + diff + `deploy-containers --limit` batches; narrow tags with `--skip-tags haproxy`; `ANSIBLE_SERIAL`; pre-pull; fact caching and pipelining; avoid global drift | [Pre-execution checklist](../operations/pre-execution-checklist.md), [Operations](../operations/index.md), [Compute scaling §8](../concepts/compute-scaling-and-performance.md#8-bottlenecks-and-optimisation-opportunities-ranked) |
