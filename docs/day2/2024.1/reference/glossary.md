# Glossary

The terms the study uses, with the place where each is defined. Each meaning holds for Kolla-Ansible `2024.1-eom`
and ansible-core 2.16.20; a term that only applied to an earlier release says so.

| Term | Meaning in this study | Defined in |
|---|---|---|
| loop-notify | When any item of a looped task changes, ansible-core 2.16.20 marks the whole task changed and notifies the handlers of every executed (non-skipped) item (`lib/ansible/executor/task_executor.py:128-130,819-820`, `lib/ansible/plugins/strategy/__init__.py:655-661`; a skipped item returns at `task_executor.py:483`). Kolla's `config.yml` and `check-containers.yml` loop over `<role>_services` with `notify: "Restart {{ item.key }} container"` (e.g. `roles/nova-cell/tasks/check-containers.yml:2-22`), so a change that concerns one container restarts every container of that role on that host [CODE]. | [Tags §2.4](../risk/tags.md#24-loop-notify-one-changed-item-notifies-the-handlers-of-all-items-code); as a finding: [Findings](findings.md#headline-findings) ([F1](findings.md#f1)) |
| `common_run` | **Ussuri only.** The per-host fact that guarded the `common` role, run through role dependencies in the first play in which a host appeared. In 2024.1 no file in `ansible/` or `tools/` mentions it: `common` is a play of its own with the `common` tag (`site.yml:88-103`), run once per run that executes that play [CODE]. | [Repository architecture §5.1](../concepts/repository-architecture.md#51-the-common-role-and-the-common_run-guard) |
| `COPY_ALWAYS` / `COPY_ONCE` (`config_strategy`) | `COPY_ALWAYS`, the default (`group_vars/all.yml:43`): `kolla_set_configs` copies the config and applies permissions on every container start. `COPY_ONCE`: only on the first start of a container (kolla `docker/base/set_configs.py:535-553`), and the restart handler then always recreates the container, so only a recreate re-applies config (`module_utils/kolla_docker_worker.py:353`, `module_utils/kolla_podman_worker.py:516`) [CODE]. | [Kolla images §2.3](../concepts/kolla-images.md#23-kolla_set_configs-copy-and-permissions), [Kolla images §3.5](../concepts/kolla-images.md#35-what-a-restart-applies); [Repository architecture §7](../concepts/repository-architecture.md#7-configuration-generation-and-overrides) (item 4) |
| `kolla_container` (`kolla_container_engine`) | **New in 2024.1.** The module that drives every container of the service roles; it replaces `kolla_docker`, which is gone, with the same 15 actions (`library/kolla_container.py:272-287`). It uses a Docker worker when `container_engine` is `docker` and a Podman worker otherwise (`library/kolla_container.py:415-420`); the roles pass `kolla_container_engine`, default `docker` (`group_vars/all.yml:92,153`) [CODE]. | [Repository architecture §6](../concepts/repository-architecture.md#6-custom-modules--container-lifecycle-via-kolla_container) |
| one-shot container | A container that Kolla-Ansible starts with `kolla_container` `start_container`, `detach: False`, `restart_policy: oneshot` and a variable that selects a branch of the image's start script (e.g. `roles/keystone/tasks/bootstrap_service.yml:33-50`); the branch ends in `exit 0` before the service command (kolla `docker/keystone/keystone/extend_start.sh:43-46`). It is started directly, not through systemd: with Docker it gets no unit file (`module_utils/kolla_docker_worker.py:338-339,381-382`); with Podman a unit file is written at creation but not used to start it (`module_utils/kolla_podman_worker.py:504,541-543`) [CODE]. In the command sections of the [Operations](../operations/index.md) pages, "One-shot" means bootstrap containers that run regardless of drift. | [Kolla images §4](../concepts/kolla-images.md#4-one-shot-containers-what-the-environment-variables-run); the convention of the command sections is in [Operations](../operations/index.md#conventions-used-by-the-command-sections) |
| drift | What `compare_container` detects: a missing container, a changed image or container parameter, a systemd unit file that would change, or `kolla_set_configs --check` reporting a difference (`module_utils/kolla_container_worker.py:58-65`). With Docker the check counts as a difference on exit 1, on an exec killed with 137, or on a failed `docker exec` (`module_utils/kolla_docker_worker.py:146-181`); with Podman on exit 1, a failed exec, or a container that is not running, and any other exit code is an error (`module_utils/kolla_podman_worker.py:428-453`) [CODE]. | [Operations, "Drift"](../operations/index.md#drift); mechanism: [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern) |
| restart vs recreate | The restart handler calls `recreate_or_restart_container`: **recreate** (stop → rm → create → start) when the image or parameters differ or under `COPY_ONCE`, otherwise **restart**, a systemd `RestartUnit` of the container's `kolla-<name>-container.service` (Docker `module_utils/kolla_docker_worker.py:341-363,439-454`; Podman `module_utils/kolla_podman_worker.py:507-524,602-616`; `module_utils/kolla_systemd_worker.py:71,106-112`). Both are full stop/start cycles; the unit's stop waits up to `docker_graceful_timeout` (60 s) (`module_utils/kolla_systemd_worker.py:32`, `group_vars/all.yml:139,151`) [CODE]. The same holds with Docker and with Podman. | [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern) |
| `flush_handlers` | `meta: flush_handlers` is where the notified restart handlers run: at the end of most `deploy.yml` (e.g. `roles/nova/tasks/deploy.yml:8-9`), or else at the end of the play. The loadbalancer role (haproxy, keepalived, proxysql) deliberately defers to the end of its play (`roles/loadbalancer/tasks/deploy.yml:8-11`) [CODE]. | [Execution flow §1](../concepts/deployment-execution-flow.md#1-how-the-order-is-decided) (row "Handler flush points"), [Execution flow §3](../concepts/deployment-execution-flow.md#3-inside-a-role-the-standard-deploy-sequence) (step 6) |
| serial / batch (`kolla_serial`, `ANSIBLE_SERIAL`) | `serial` splits a play into batches; each batch completes the whole play, handlers included, before the next starts (ansible-core 2.16.20 `lib/ansible/executor/playbook_executor.py:181-190`). For `reconfigure` and `upgrade` the wrapper sets `kolla_serial` from `ANSIBLE_SERIAL` (`tools/kolla-ansible:296,522,531`); for `deploy`, pass `-e kolla_serial=N` yourself (`tools/kolla-ansible:490-493`). **Changed in 2024.1:** the etcd play has no `serial` key, so `kolla_serial` does not batch it (`site.yml:470-481`) [CODE]. | [Execution flow §5](../concepts/deployment-execution-flow.md#5-batching-serial-and-its-interaction-with-order), [Execution flow §1](../concepts/deployment-execution-flow.md#1-how-the-order-is-decided); [Repository architecture §2](../concepts/repository-architecture.md#2-from-cli-to-ansible-playbook) |
| `max_fail_percentage` | **New in 2024.1.** Set on almost every play from `<service>_max_fail_percentage`, then `kolla_max_fail_percentage`, then 100 (e.g. `site.yml:95-99`). ansible-core 2.16.20 compares the hosts failed in the current batch with the batch size (`lib/ansible/plugins/strategy/linear.py:336-348`, `lib/ansible/executor/task_queue_manager.py:332-338`), so with the default 100 it never stops a play early [CODE]. | [Execution flow §5](../concepts/deployment-execution-flow.md#5-batching-serial-and-its-interaction-with-order) |
| `run_once` / `delegate_to` | `run_once`: the task runs once per play, or once per batch when `kolla_serial` > 0, since each batch is a separate run of the play and `run_once` only ends the host loop of that run (ansible-core 2.16.20 `lib/ansible/executor/playbook_executor.py:181-190`, `lib/ansible/plugins/strategy/linear.py:181,207-209`) [CODE]. `delegate_to`: the step runs on another host; `groups['<grp>'][0]` is the target of almost every `run_once`/`delegate_to` bootstrap step, including for hosts outside `--limit`. | [Tags §2.5](../risk/tags.md#25-run_once-with-serial-code); [Repository architecture §8](../concepts/repository-architecture.md#8-inventory-model); [Reconfigure a single service §2](../operations/reconfigure-a-service.md#2-execute-a-service-specific-tag-implicit-effects) (row "Actions on hosts outside `--limit`") |
| `genconfig` | The CLI command for `kolla_action=config` (`tools/kolla-ansible:557-560`): it writes the config, compares no container, and all container restarts are skipped. **Changed in 2024.1:** the common role's config step runs `ensure_image` on the fluentd image, which pulls it when it is absent (`roles/common/tasks/config.yml:42-51`) [CODE]. The Ussuri exception, the nova-hyperv handlers, does not exist: 2024.1 has no nova-hyperv role ([Pre-execution checklist](../operations/pre-execution-checklist.md)). | [Execution flow §4](../concepts/deployment-execution-flow.md#4-action-matrix-what-each-kolla_action-does) (row `genconfig`); [Repository architecture §2](../concepts/repository-architecture.md#2-from-cli-to-ansible-playbook) |
| `deploy-containers` | Runs the role's `deploy-containers.yml` (`tools/kolla-ansible:499-501`), which in 50 of the 53 roles that have one is only `import_tasks: check-containers.yml` (e.g. `roles/nova-cell/tasks/deploy-containers.yml:2`), plus the handlers it notifies: no config is written, and no bootstrap, Keystone registration or loadbalancer configuration runs (the loadbalancer includes require `deploy`, `reconfigure`, `upgrade` or `config`, `site.yml:324-326`). The exceptions are mariadb, which also looks up the cluster (`roles/mariadb/tasks/deploy-containers.yml:2-5`), swift, which runs its `start.yml` (`roles/swift/tasks/deploy-containers.yml:2`), and ceph-rgw, whose file is empty [CODE]. | [Execution flow §4](../concepts/deployment-execution-flow.md#4-action-matrix-what-each-kolla_action-does) (row `deploy-containers`); [Write config first, apply in controlled batches §1.1](../operations/controlled-batches.md#11-compute-changes-in-controlled-batches-recommended-pattern) |
| `KOLLA_BOOTSTRAP` / `KOLLA_UPGRADE` / `KOLLA_OSM` | Variables, sent with an empty value (`module_utils/kolla_container_worker.py:576-578`), that select a one-shot branch of an image's start script; the branch tests only whether the variable is set (e.g. kolla `docker/keystone/keystone/extend_start.sh:43`). What each one runs differs per image [CODE]. | [Kolla images §4](../concepts/kolla-images.md#4-one-shot-containers-what-the-environment-variables-run) |
| [CODE] / [NOT AVAILABLE] | The two evidence labels: shown by the sources, with a `path:line` citation nearby; or not established by the sources. The fact sheets use FACT and NOT AVAILABLE for the same two levels. | [Conventions and evidence labels](../start/conventions.md#evidence-labels) |
| `kolla_action` | The extra-var that the wrapper passes with a sub-command (`-e kolla_action=<action>`, e.g. `tools/kolla-ansible:490-493`); every service role's `tasks/main.yml` is a dynamic `include_tasks: "{{ kolla_action }}.yml"` (e.g. `roles/nova-cell/tasks/main.yml:2`) [CODE]. | [Repository architecture §2](../concepts/repository-architecture.md#2-from-cli-to-ansible-playbook), [Repository architecture §4.1](../concepts/repository-architecture.md#41-kolla_action-dispatch) |
| `compare_container` | The `kolla_container` action run by `check-containers.yml` (e.g. `roles/nova-cell/tasks/check-containers.yml:4-5`): it compares the container's definition and its systemd unit file, and runs `kolla_set_configs --check` inside the running container (`module_utils/kolla_container_worker.py:58-65`) [CODE]. | [Repository architecture §4.3](../concepts/repository-architecture.md#43-the-config--check--handler-pattern) |
| `kolla_set_configs --check` | The in-container check whose exit code decides config drift. It compares only the `config_files` entries of `config.json` (kolla `docker/base/set_configs.py:556-559`); the file is unchanged since 2023.1 [CODE] ([F14](findings.md#f14)). | [Kolla images §3](../concepts/kolla-images.md#3-kolla_set_configs---check-what-it-compares-and-its-exit-codes); by hand: [Predict and inspect a run](../operations/predict-a-run.md) |
| `config.json` (`config_files`, `command`, `permissions`) | The manifest, read from `/var/lib/kolla/config_files/config.json`, that tells `kolla_set_configs` which files to copy to their final location, and names the command to start, written to `/run_command` (kolla `docker/base/set_configs.py:279-299,302-316`) [CODE]. | [Repository architecture §7](../concepts/repository-architecture.md#7-configuration-generation-and-overrides) (item 4); [Kolla images §2.3](../concepts/kolla-images.md#23-kolla_set_configs-copy-and-permissions) |
| global inputs | `enable_*` flags, group membership and passwords, which are rendered into per-host files on every host. Examples: the RPC transport URL lists every host of the RPC group with its password (`group_vars/all.yml:243,248`), and the cron logrotate list follows the global `enable_*` flags (`roles/common/tasks/config.yml:205-214`) [CODE]. | [Component dependencies §5](../components/dependencies.md#5-compute-node-dependency-summary); [Why a small change creates a large workload](../risk/small-change-large-workload.md) |
| waves, forks | A task on *H* hosts needs ⌈H/F⌉ waves, where *F* is the number of forks. This is a counting model: ansible-core 2.16.20 starts at most min(forks, batch size) workers and queues a host's task only on a free worker (`lib/ansible/executor/task_queue_manager.py:320-321`, `lib/ansible/plugins/strategy/__init__.py:397-425`) [CODE]. | [Compute scaling §1](../concepts/compute-scaling-and-performance.md#1-how-ansible-core-216-spends-time-in-kolla-ansible), [Compute scaling §4.1](../concepts/compute-scaling-and-performance.md#41-model) |
| scope legend D, Ctl, C, C×S, H, Cond | How often a task runs: once per deployment, per controller, per compute, per compute and container, per host, or only when a condition holds. | [Compute scaling §3](../concepts/compute-scaling-and-performance.md#3-expensive-tasks-and-their-scaling-factors) |
| R*n*, F*n*, Q*n* | Risk numbers [R1–R30](../risk/risk-register.md#r1), finding numbers [F1–F17](findings.md#f1) and open-question numbers [Q1–Q21](../troubleshooting/open-questions.md#q1). Each risk, finding and question is a section with its own anchor, so links to them land on the item. | [Risk register](../risk/risk-register.md#matrix); [Findings](findings.md#headline-findings); [Open questions](../troubleshooting/open-questions.md) |
